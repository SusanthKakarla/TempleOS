- (constraint) Existing tenant login is Firebase phone identity plus tenant host lookup plus persons and active tenant_memberships; do not reintroduce admin_users.
- (decision) Use role codes for human identity/category labels such as admin, priest, committee_member, volunteer, and use a separate tenant_member_permissions assignment table for fine-grained access control.
- (decision) Temple admin role is the only tenant-side authority allowed to invite staff, change roles, change per-member permissions, disable members, or view permission-management screens.
- (decision) Every dashboard page and API route must check tenant feature availability and member permissions separately: feature flags decide whether the temple bought or enabled a module; permissions decide whether this logged-in member may use it.
- (decision) Permission keys are capability verbs scoped to dashboard modules, e.g. donations.view, donations.manage, devotees.view, devotees.manage, events.view, events.manage, campaigns.view, campaigns.manage, settings.manage, users.manage.
- (decision) Admin remains a privileged role with implicit full tenant permissions for V1 so last-admin protection continues to work; explicit permissions are required for non-admin roles.
- (decision) Session payload should keep identity and roles only; effective permissions are loaded server-side from Postgres through the auth guard so permission changes take effect without waiting for cookie expiry.
- (decision) Permission assignment rows carry tenant_id and membership_id and use the existing tenant_memberships id plus tenant_id uniqueness to prevent cross-tenant grants at the database layer.
- (decision) Role selection in the user-management UI should auto-check common default permissions for that role; temple admin can adjust before saving.
